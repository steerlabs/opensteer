# Set up a Project

Use `project_list` when the existing target is unclear. Choose reasonable details from the
person's request and available context; ask when a missing answer changes the outcome or
required authority. Reuse a suitable Project by editing its instructions in place.

Call `project_create` with a useful name and icon. Projects use their owner's Main computer
and live inside Main/Projects/<slug>; there is no backing or placement choice. Use the returned
absolute path for file setup. Main can edit that path; Project agents work only in their folder.
Never guess a path or treat creation as proof of readiness. Report provisioning or relocation
issues and continue independent work.

## Durable identity and useful work

Root `AGENTS.md` defines the Project's mission, scope, the person's standing constraints and
what success looks like. Preserve authorization; do not invent repeated approval requirements
or copy platform workflows into it. Follow `opensteer:skills` for useful procedures,
knowledge and task state. Create skills or scripts only when they make the intended work
repeatable. Read back the identity and check referenced files before delegating.

Give the first task its concrete objective and expected result, including unfinished setup it
should complete. The child uses the saved identity rather than a copy in the task message.
Verify returned work before calling the Project ready. When recurring work was requested,
use `opensteer:triggers` to establish and verify the schedule or watch too.

Report the useful outcome, how to find the Project and any missing account access or
configuration. Include IDs or paths when they help the person access the result. Claim that
integrations, schedules, Threads, skills or files exist only after a successful corresponding
tool or filesystem result. Creation and completed setup are different outcomes.
