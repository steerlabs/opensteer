# Editing Admission

One rule governs where a remote edit, command, or clipboard action may land across the browser runtime, the Mac helper, and the phone browsers. An operation is applied only when what it assumes is true of the **live** field at the moment it goes in.

## The Five-Part Rule

1. **Field identity.** Every operation assumes the same field is focused. A field's identity is the element itself plus its kind/role, whether it is sensitive (e.g., password), and whether it is editable (`fieldKey` on the browser; `AXUIElement` + role + `secure` on the Mac helper). A different element, a recreated element, a blur-and-refocus, or an element whose sensitivity or kind changed is a **different field** and clears all earlier contexts.
2. **Caret-relative edits.** An insertion (`before === "" && after === "" && text !== ""`), the single backward deletion (`deleteBackward`), a plain caret move (`moveBackward`, `moveForward`), or a paste/cut/copy assumes the same field.
   - **Current vs. earlier context (collapsed live selection):** Under the **current** context (`contextId === current`), a caret-relative edit is applied as now. Under an **earlier** context of the same field (up to 64 kept), a mutating caret-relative edit (insertion, `deleteBackward`, plain caret move, paste, or cut) assumes a caret and is applied **only when the live selection is collapsed**; if the page or app has made a non-empty selection the viewer never saw, it is refused without rotating the context.
   - **One dependency rule (every side):** An operation computed from another is not applied when that one was refused — the removal of a selection, the moves that compensate, and the insertion or paste that replaces it.
     - **Browser:** the compensating moves (`input.command`), replacement insertion (`input.text`), and replacement paste (`clipboard.paste-data` / `clipboard.paste`) carry `follows: true` and are refused when the same producer's preceding edit under that context was refused.
     - **Display targets (Mac helper, Agent Phone):** the removal, its compensating moves, and its replacement insertion or paste travel in **one** `display.input` batch (`DisplayEditingSession.sendBatch`), never split across batches (if a dependent group exceeds one batch it is refused whole), and both receivers stop the batch at its first refusal.
   - A page-level paste, copy, or cut made while no editable field is focused carries the page's own no-field context and is valid only while no editable field has focus.
   - **Clipboard settlement:** A clipboard operation is settled only by an answer that names it (`clipboard.result` carrying its `operationId`), or by the end of what carries it (disconnect/close of the session or surface, or the two session-wide reasons `unsupported-operation` / `target-suspended`). An unrelated `browser.error` settles nothing. When the carrier ends with a paste already sent, the outcome is `unknown` (never `refused`) and the viewer never invites a blind second paste.
3. **Text-naming edits.** A replacement (`before !== ""` or `after !== ""`, such as autocorrect or deleting named text) also assumes that named text is present around a collapsed caret.
   - **Mac helper:** Valid when the same field is focused (current or earlier context of that field) AND the live text around the collapsed caret matches `before` and `after`. Because an app such as Electron can render a prior keystroke after its dispatch returns, edits run in order and a text-naming edit whose named text is not yet present waits up to **0.5 s** for it to appear (aborting immediately if focus leaves the field), then is refused.
     - **Known residual (S8, repeated word):** Because the Mac helper accepts an earlier context when the live text around a collapsed caret matches `before`/`after`, if the field holds a repeated word (e.g. `"foo foo"`), an external caret move lands at the other occurrence (offset 3 instead of offset 7), and a replacement of `"foo"` under an earlier context is still in flight, it will match and replace the occurrence at the live caret. The browser/Mac split accepts this rare residual so autocorrect works across late-rendering Mac apps.
   - **Browser runtime (why exact context stays):** On the browser, replacements keep the exact-context + `selectionRevision` requirement in addition to live text matching. Chromium applies keystrokes synchronously in the renderer's input lane (so there is no post-dispatch lag), and the page script observes every selection change synchronously with `selectionRevision`. Accepting an earlier context on live text alone would allow a replacement computed for one occurrence of a repeated word to overwrite another occurrence after an external caret move (e.g., `"foo foo"` with caret moved from offset 7 to offset 3: `apps/browser-runtime/src/browser/editing.test.ts`, `"same-field caret move invalidates verified replacement"`).
4. **Exact-context commands and live compositions.** A command with nothing to check against the live text (`selectAll`, `undo`, `redo`, `deleteForward`, moves by word/line/paragraph/document, selection-extending moves) and live composition updates (`input.compose`) require the exact current context (`contextId === current`).
5. **Context changes.** A context changes only when what it identifies changes:
   - Focus moves to another field, blurs, or changes kind/sensitivity/editability: new `contextId`, all earlier contexts cleared.
   - Same field's content or selection changes **by someone else** (an outside edit, external caret move, agent mutation, or the app altering what was typed): new `contextId`, previous **published** `contextId` retained in `earlier` (FIFO bound 64; unpublished contexts rotated while batches are pending are never placed in `earlier`, so bursts never evict the viewer's published context).
   - **Own edit effects (Mac helper & browser):** The viewer's own edits do not rotate the context. On the browser, `beginInput`/`finishInput` re-anchors without bumping `selectionRevision`. On the Mac helper, after dispatching one of the phone's own edits it records the expected resulting state in a short per-lease queue: an observed state equal to the state before (the app has not caught up yet) or equal to the expected state after any prefix of unanswered own edits is its own effect and rotates nothing; any other observed state (such as an app rewriting or auto-capitalizing what was typed) rotates, publishes a new context, and clears the expected queue.
   - A text-naming replacement mismatches the live field (while a field is focused): new `contextId` (so the viewer resets its stale mirror), previous published `contextId` retained in `earlier`.
   - A key going up, a mouse button, a scroll, or a refusal for wrong context, wrong field, no focused field, sensitivity, or unsupported action changes **no** context and forgets **nothing**.

## Phone Browsers and Agent Phone (Field-Only Contexts)

Phone browsers (`apps/mobile/src/phone-browser/manager.ts`, Android `ViewerInput.kt`, iOS `PhoneBrowserWire.swift` / `PhoneBrowserClipboard.swift`) and Agent Phone (`OwnerEditing.kt`) identify the focused field only (rotating on focus change or navigation, not on every content change; Agent Phone rotates on focus or selection change). Consequently, Rules 2 and 4 reduce there to exact equality on the field's current `contextId` ("same field"). For Rule 3 (text-naming edits, `before !== "" || after !== ""`):

- **Phone browsers** (`manager.ts` via `browserBasicInputAllows`, Android `ViewerInput.kt`, iOS `PhoneBrowserWire.swift`) refuse text-naming edits outright (`unsupported-operation` / `notActionable`) because phone browsers use basic input without range replacement.
- **Agent Phone** (`OwnerEditing.kt`) refuses text-naming edits as `unsupported` below API 33, and on API 33+ reads `getSurroundingText` and verifies the live collapsed caret and exact `before`/`after` text match before replacing.

## What Carries a Context

- **Browser runtime:** `input.text`, `input.compose`, `input.command`, `clipboard.paste-data`, `clipboard.paste`, `clipboard.cut`, `clipboard.copy`. (`input.key` carries none, by design.)
- **Phone browsers (Android & iOS):** `input.text`, `input.compose`, `input.command`, `clipboard.paste-data`, `clipboard.paste`, `clipboard.copy` (`clipboard.cut` is unsupported). (`input.key` carries none, by design.)
- **Mac helper (`display.input`):** `edit`, `command`, `paste` (with text), `copy`, `cut` (refused as unsupported on Mac). (`key`, `mouse`, `scroll` carry none, by design.)
